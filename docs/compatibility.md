# Compatibility

pyroid's claim is not "close to" the libraries it replaces but **the same output**. This page is the
evidence: what each module is compared against, by which rule, and how many comparisons have been
made. Every known difference is listed in the module's guide.

## How parity is tested

Each module is tested **differentially**: the same input goes to pyroid and to the incumbent, and
the results are compared exactly (for fastText, probabilities are also allowed to differ by
1e-6, though none do; the metrics are compared as the strings they print, with no tolerance). The
inputs are:

- **Pinned real documents:** the first 10,000 FineWeb documents, 8 FineWeb-2 languages, and a
  seeded adversarial set of 3,232 documents (mojibake, near-duplicates, edge cases), all
  fixed by sha256. The metrics use pinned evaluation data instead: CNN/DailyMail, SummEval and
  the WMT21 system outputs.
- **The incumbent's own test corpus** where it has one (ftfy's 161 golden cases, including its
  10 known failures, which pyroid reproduces too; json_repair's test suite, replayed call by call).
- **Property-based fuzzing** with [Hypothesis](https://hypothesis.readthedocs.io/), with
  strategies that reach lone surrogates, every option value and every documented edge case.
  Hypothesis never generates surrogates by default; these strategies do.
- **Exceptions:** for invalid input, the exception *type* must match too (messages may differ).

The suites run against the installed wheel, on regular and free-threaded CPython. They also have
teeth: deliberately broken builds (e.g. ftfy without surrogate-pair joining) fail them.

## Interpreters and Unicode versions

Results that depend on the Python version (ftfy's and datatrove's use of `\w`, `\d` and
`isalpha`, json_repair's `str.isspace` and friends, and Unicode normalization) are matched **per
interpreter**. pyroid carries Unicode tables for 14.0, 15.0, 15.1, 16.0 and 17.0 (CPython 3.11
to 3.15) and picks the one matching `unicodedata.unidata_version`. The ftfy suites passed on
CPython 3.11, 3.12, 3.13, 3.14, 3.14t, 3.15 and 3.15t; the other suites ran on 3.12 or 3.13 and on
free-threaded 3.15t, as their rows say. A few references can't be loaded on a free-threaded build
without re-enabling the GIL (sacrebleu imports lxml), so their live checks run on GIL builds only.

## Languages

The filters and dedup suites cover English and 8 FineWeb-2 languages end to end, and the
tokenizer replays cover every natively supported datatrove tokenizer: 3,999 of datatrove's 4,343
language codes. The rest go through datatrove's own Python tokenizers
(`python_tokenizer=True`), so they are datatrove's results by construction. See
[Languages](guides/languages.md).

## Platforms

**Linux aarch64** (Docker/OrbStack VM) is where every suite on this page ran.

**Linux x86_64** was verified **under emulation** (OrbStack with Rosetta 2, whose CPU has SSE4.2,
FMA and BMI2 but no AVX or AVX2), on CPython 3.12 and 3.15t, with the release wheels:

- `python/tests`: 1,850 passed on 3.12 and 1,678 on 3.15t (GIL off), 0 failed.
- The ftfy, fastText, filters and dedup parity suites: 0 differences (filters: 66,160 decisions;
  dedup: 13,232 signatures and the removed set), and the live datatrove oracle job: 44 passed.
- **fastText:** pyroid's x86_64 output is bit-identical to x86_64 fasttext-predict 0.9.2.4 on all
  26,464 pinned predictions (`max |Δp| = 0`).
- **Per-platform references.** fastText's own output differs between architectures for the
  quantized `lid.176.ftz` (on 10,837 of 13,232 documents, by at most 5.96e-7; the labels are the
  same), because its aarch64 build fuses multiply-adds that baseline x86-64 can't. pyroid
  reproduces each architecture's arithmetic, so the fastText reference is pinned per platform.
  The metrics reference is too: regenerated on x86_64, 165 of its 694,757 BLEU results differ by
  one ulp (the C library's `exp` and `log`); pyroid matches the x86_64 reference exactly
  (1,307,887 checks, 0 differences).
- Not yet run on x86_64: the json_repair suite, the multilingual cases and the newer datatrove
  steps.

GitHub's x86_64 runners have AVX2 and may pick other `exp`/`log` variants in glibc than the
emulator did, so the x86_64 references are re-checked on the first CI run. pyroid and the
reference share the C library, so they would still agree with each other.

**macOS, Windows and musl** are unverified until the release workflow's first run. pyroid fuses
fastText's multiply-adds on every aarch64 target, as Linux builds of fastText do; macOS (clang),
Windows (MSVC) and musl builds of fastText may round the last bit differently from that, and
exact ties between labels are ordered as libstdc++ orders them. Labels and the 1e-6 tolerance are
expected to hold. pyroid's x86 builds stay at baseline x86-64 (no `-C target-cpu`), as
bit-identity with baseline fastText builds requires.

## Hardening

Beyond parity, the native code was checked for crashes and undefined behaviour (2026-11-06,
Docker):

- **Fuzzing** (cargo-fuzz): 7 targets (ftfy, filters, the tokenizer, translit, dedup, fastText
  model loading and inference, the Arrow importer), about 4.4 hours and 19.8 million executions,
  each target for at least 25 minutes. No crashes in the product code; one resource bug was fixed
  (a tiny crafted fastText model could make every vector call allocate 8 GiB; pyroid now rejects
  it, where fastText loads it). The fuzzers' results over their final corpora also matched ftfy,
  datatrove, spaCy and anyascii.
- **Miri** (Stacked and Tree Borrows, strict provenance, symbolic alignment, 16 seeds on the
  thread tests) on the Arrow FFI code: no undefined behaviour. **AddressSanitizer** and
  LeakSanitizer: clean. The pure-Rust core forbids `unsafe`.
- **MSRV:** Rust 1.85, checked with a real 1.85 build.
- **Supply chain:** `cargo deny` advisories over the Rust dependencies, and `pip-audit` over the
  locked test, parity and benchmark dependency sets: no findings.

# Compatibility

pyroid aims for the same output as the libraries it replaces, not output close to it. This page
is the evidence: what each module is compared against, by which rule, and how many comparisons
have been made. Every known difference is listed in the module's guide.

## How parity is tested

Each module is tested differentially: the same input goes to pyroid and to the incumbent, and the
results are compared exactly. For fastText, probabilities may also differ by 1e-6, though none
do. The metrics are compared as the strings they print, with no tolerance. The inputs are:

- Pinned real documents: the first 10,000 FineWeb documents, 8 FineWeb-2 languages, and a seeded
  adversarial set of 3,232 documents (mojibake, near-duplicates, edge cases), all fixed by
  sha256. The metrics use pinned evaluation data instead: CNN/DailyMail, SummEval and the WMT21
  system outputs. Trafilatura uses 7,192 pinned Common Crawl pages from 3 crawls, as datatrove's
  WARC reader and URL filter pass them on.
- The incumbent's own test corpus, where it has one. For ftfy that is its 161 golden cases,
  including its 10 known failures, which pyroid reproduces too. The test suites of json_repair
  and Trafilatura are replayed call by call.
- Property-based fuzzing with [Hypothesis](https://hypothesis.readthedocs.io/), with strategies
  that reach lone surrogates, every option value and every documented edge case. Hypothesis
  never generates surrogates by default; these strategies do.

For invalid input, the exception type must match too (messages may differ).

The suites run against the installed wheel, on regular and free-threaded CPython. Deliberately
broken builds (for example ftfy without surrogate-pair joining) fail them.

## Interpreters and Unicode versions

Results that depend on the Python version are matched per interpreter. That covers ftfy's and
datatrove's use of `\w`, `\d` and `isalpha`, json_repair's `str.isspace` and friends, and Unicode
normalization. pyroid carries Unicode tables for 14.0, 15.0, 15.1, 16.0 and 17.0 (CPython 3.11
to 3.15) and picks the one matching `unicodedata.unidata_version`.

The ftfy suites passed on CPython 3.11, 3.12, 3.13, 3.14, 3.14t, 3.15 and 3.15t. The other suites
ran on 3.12 or 3.13 and on free-threaded 3.15t, as their rows say. A few references can't be
loaded on a free-threaded build without re-enabling the GIL (sacrebleu imports lxml), so their
live checks run on GIL builds only.

### Per-platform references

fastText's own output differs between architectures for the quantized `lid.176.ftz`: on 10,837
of 13,232 documents, by at most 5.96e-7, with the same labels. Its aarch64 build fuses
multiply-adds that baseline x86-64 can't. pyroid reproduces each architecture's arithmetic, so
the fastText reference is pinned per platform, and pyroid's x86_64 output is bit-identical to
x86_64 fasttext-predict 0.9.2.4 on all 26,464 pinned predictions (`max |Δp| = 0`).

The C library matters as well. pyroid calls the platform's `exp`, `expf` and `log`, as fastText
does, and glibc, musl, Apple's libm and Windows' UCRT round some of them differently: on GitHub's
runners (2026-11-10), 39 of the 54 test-zoo models gave other digests on macOS arm64, 16 on macOS
x86_64 and 14 on Windows x64, with the same model files. So the zoo digests are pinned per OS, C
library and architecture; on each platform they were the same for every Python version and for the
PGO release wheels. On Windows x64, pyroid matched fasttext-predict to the last bit over 316
(model, k) pairs. On macOS the largest difference was 1.91e-6, on a test model with weights scaled
by 20, where fasttext-predict's clang build rounds its dot products differently.

The metrics reference is pinned per platform the same way, because sacrebleu's BLEU calls the C
library's `exp` and `log`. Its difference came only from Rosetta 2's emulated CPU, which has
SSE4.2, FMA and BMI2 but no AVX or AVX2, so glibc took other `exp`/`log` paths there. On the c7i,
with AVX2 and FMA, the x86_64 and aarch64 files are the same. GitHub's x86_64 runners have AVX2
too, and CI re-checks the references on its first run. pyroid and the reference share the C
library, so they would agree with each other either way.

### macOS, Windows and musl

These are unverified until the release workflow's first run. pyroid fuses fastText's
multiply-adds on every aarch64 target, as Linux builds of fastText do. macOS (clang), Windows
(MSVC) and musl builds of fastText may round the last bit differently from that, and exact ties
between labels are ordered as libstdc++ orders them. Labels and the 1e-6 tolerance are expected
to hold. pyroid's x86 builds stay at baseline x86-64 (no `-C target-cpu`), as bit-identity with
baseline fastText builds requires.

## Hardening

Beyond parity, the native code was checked for crashes and undefined behaviour on 2026-11-06, in
Docker:

- Fuzzing with cargo-fuzz: 7 targets (ftfy, filters, the tokenizer, translit, dedup, fastText
  model loading and inference, the Arrow importer), about 4.4 hours and 19.8 million executions,
  each target for at least 25 minutes. There were no crashes in pyroid's code. One resource bug
  was fixed: a tiny crafted fastText model could make every vector call allocate 8 GiB. pyroid
  now rejects it, where fastText loads it. The fuzzers' results over their final corpora also
  matched ftfy, datatrove, spaCy and anyascii.
- Miri (Stacked and Tree Borrows, strict provenance, symbolic alignment, 16 seeds on the thread
  tests) on the Arrow FFI code: no undefined behaviour. AddressSanitizer and LeakSanitizer:
  clean. The pure-Rust core forbids `unsafe`.
- MSRV: Rust 1.85, checked with a real 1.85 build.
- Supply chain: `cargo deny` advisories over the Rust dependencies, and `pip-audit` over the
  locked test, parity and benchmark dependency sets. No findings.
